SECTION 3: ORCHESTRATION ORDER PER TURN (from user input to GPT response)
================================================================================

The pipeline processes each message through a strict 10-step flow.
Steps 1-6c are PRE-GPT (local, deterministic). Steps 7-9 are POST-GPT (local, no second GPT call).

--- PRECONDITION: Pre-chat Guard (app/(tabs)/chat.tsx) ---

  Before the pipeline is ever called:
  - Elias users MUST submit VSP via prechat-vsp.tsx (thermometer, no default)
  - Kim users MUST submit Eigen Regie via prechat-eigen-regie.tsx (slider, interaction required)
  - Chat screen blocks until pre-chat input is confirmed
  - Pipeline never receives vsp=null in normal flow (isBlocked is safety guardrail only)

--- STEP 0: MODULE 12 PRE-ANALYSIS FAILSAFE ---

  Check: does the user have ANY meaningful context?
  (sliders, backpack content, diary, trigger history, or session history)
  If NO context at all: return passive response asking user to fill in data.
  If YES: proceed to pipeline.

--- PRE-GPT STEP 1: Apply Trigger Decay to PREVIOUS Buffer State ---

  - Decay runs on OLD state BEFORE new message merges
  - Prevents new matches from resetting/distorting decay too early
  - Calls analyzeBackpackRelevance('', ...) with empty message to advance decay counters
  - Trigger decay rules: -1 per 2 messages without match, -2 per 5 minutes inactivity

--- PRE-GPT STEP 2: Update ShortTermMemoryBuffer with New Message ---

  - Buffer update happens AFTER decay
  - New message data merges into decayed state
  - Computes: zoneScore, zoneColor, currentEmotion, currentIntent, currentTriggerGuess
  - Zone score boundaries: 0-20=GREEN, 21-40=YELLOW, 41-60=ORANGE, 61-80=RED, 81-100=PURPLE

--- PRE-GPT STEP 3: Apply RegulationDecayEngine Zone Decay ---

  - Runs AFTER buffer update (uses new zone score context)
  - Three decay types:
    * TIME DECAY: -2 to -4 per cycle if no strong trigger
    * RESPONSE DECAY: -5 to -15 if user intensity clearly drops
    * OVERSHOOT CORRECTION: up to -20 if user shifts sharply from high to calm
  - Result applied to buffer zone score

--- PRE-GPT STEP 4: Analyze State + Select DominantState ---

  - analyzeState(rugzak, userMessage) → StateAnalysis
  - detectInputSignals(message) → InputSignals
  - selectDominantState(buffer, analysis, signals) → DominantState
  - DominantState = { dominantModule, dominantTrigger, dominantDirection, dominantTone, riskScore, selectionReason, sourceLayer }

--- PRE-GPT STEP 5: Build BufferSnapshot + Regulation + Relevance ---

  5a. getBufferSnapshot(buffer) → BufferSnapshot (stable snapshot for GPT payload)
  5b. applyRegulation(buffer, previousAssistantMessage, guidanceDepth) → RegulationResult
      - Maps zone color to action: GREEN→reflect, YELLOW→slow_down, ORANGE→regulate, RED→stabilize, PURPLE→ground
      - Anti-repetition: if previous message already contained regulation, soften or skip
      - Guidance depth ceiling: RED/PURPLE→force 'light', ORANGE→cap 'normal', YELLOW/GREEN→user setting
  5c. analyzeBackpackRelevance(message, backpack, userDat, sliders, dominantModule) → BackpackRelevanceResult
      - Trigger scoring (threshold >= 4, max 2 triggers, weak second trigger dropped)
      - Core wound detection (linked to trigger or message)
      - Context line extraction (from life story)
      - Relationship anchor detection

--- PRE-GPT STEP 6: Engine Decision + Routing + Intervention Continuity ---

  6a. Create engine decision:
      - Elias: createEliasDecision(input) → EliasDecision
        Flow: computeEliasZone() → resolveEliasZone(vsp, computed) → computeEliasImpact(resolved)
        If isBlocked: HARD STOP → return { status: 'BLOCKED_PRECHAT_REQUIRED' }
      - Kim: createKimDecision(input) → KimDecision
        Flow: processEigenRegie(score) → computeKimZone(result) → KimDecision

  6b. routeEngineDirective({ userType, eliasZone, kimZone }) → EngineDirective | null
      - Pure routing: Elias users get EliasDirective, Kim users get KimDirective
      - Never merges both

  6c. Intervention Continuity (Elias only):
      - evaluateInterventionContinuity(resolvedZone, userMessage) → InterventionState | null
      - Compares current resolvedZone with linkedZone from previous turn
      - Zone shifted → re-evaluate (wasReEvaluated = true)
      - Zone stable → continue same line (wasReEvaluated = false)
      - Detects user response pattern (engaged/deflected/escalated/ignored/unknown)
      - Computes effectiveness score (0-100)
      - Returns null on first turn (no previous intervention)

--- GPT CALL ---

  - Assemble ChatContext from all pre-GPT outputs
  - buildGPTPayload(context) → GPTPayload
  - OpenAI provider sends to server:
    * SESSION_INIT: full payload (backpack, userDat, diary, all static + dynamic fields)
    * LIVE_MESSAGE: dynamic fields only (static cached server-side after SESSION_INIT)
  - Server buildSystemPrompt() assembles full system prompt (see Section 5)
  - Model routing: gpt-4o for SESSION_INIT/crisis/high-risk/complex modules, gpt-4o-mini otherwise
  - ONE GPT call per message (never two)

--- POST-GPT STEP 7: Update Internal Stored State ---

  - Add user message to chatHistory
  - Add AI response to chatHistory
  - Update buffer with assistant response
  - DO NOT reselect dominantState (pre-GPT state is the decision variable)
  - updateInterventionAfterResponse(resolvedZone, regulationAction) — records what Elias actually did

--- POST-GPT STEP 8: Concrete Pattern Marking ---

  - Mark pattern signals from buffer trigger guess and dominant state trigger
  - Increment repeat counters (session-level only)
  - Threshold for promotion candidacy: repeatCount >= 3 (PROMOTION_THRESHOLD)
  - Actual promotion only happens at session end (Step 10)
  - Cooldown: 24 hours between promotions of same pattern

--- POST-GPT STEP 9: Consolidated Logging ---

  - Log all pre-GPT decisions, GPT model/tokens, post-GPT state
  - Record token cost to session budget tracker
  - Return PipelineResult to caller

--- SESSION-END STEP 10: Ranked Promotion Evaluation ---

  - Triggered when user ends session (not per-message)
  - Evaluate all pattern signals with repeatCount >= PROMOTION_THRESHOLD (3)
  - Rank by score (not FCFS)
  - Apply top 5 promotions to user.dat
  - Cooldown enforcement: 24h per pattern

--- SERVER: buildSystemPrompt() — INJECTION ORDER ---

The system prompt is assembled in this exact order:

=== SESSION_INIT PROMPT STRUCTURE ===

  1. IDENTITY
     - ELIAS_IDENTITY_PROMPT or KIM_IDENTITY_PROMPT
     - Full persona definition, therapeutic approach, communication style

  2. ANTI-HALLUCINATION PROTOCOL (Module 033)
     - Absolute rule: never fabricate information about the user
     - "Bij twijfel: VRAAG"

  3. SCHEMA RECOGNITION (Elias only)
     - ELIAS_SCHEMA_RECOGNITION block

  4. STOA SESSIONS (Elias only)
     - ELIAS_STOA_SESSIONS block

  5. USER NAME INSTRUCTION
     - "De naam van de gebruiker is {name}. Spreek hen af en toe bij naam aan."

  6. IDENTITY MEMORY (from backpack)
     - Life story sections (marked as sacred, never summarize)
     - Intake context (initial emotion, urgency, date)
     - Recognition instruction

  7. DIARY MEMORY
     - Recent diary entries with dates and mood tags
     - "Citeer hun dagboek NIET ongevraagd terug."

  8. SESSION MEMORY (from userDat)
     - Known trigger patterns (with counts and dates)
     - Mood trajectory (last 5 check-ins)
     - Module usage history
     - Previous session analyses (themes, triggers, mood deltas)

  9. RELEVANCE CONTEXT (full, for session start)
     - Active triggers (scored)
     - Core wound
     - Context line from life story
     - Relationship anchor
     - Relational pattern (if confidence >= 0.35)
     - Stage of Change (with full description)
     - Recent diary notes

  10. === VERPLICHTE GEDRAGSINSTRUCTIES === (mandatory behavior block)
      a. STANCE (therapeuticStance)
      b. GUIDANCE DEPTH INSTRUCTION (light/normal/deep with specific rules)
      c. REGULATION INSTRUCTION (if regulation action != reflect)
         - Zone-specific GPT instruction (slow_down/regulate/stabilize/ground)
         - May be softened if previous message already regulated
      d. ENGINE DIRECTIVE BLOCK
         - Engine type (ELIAS/KIM)
         - Zone level + label
         - Impact values (interventionLevel, reflectionDepth, directiveStyle for Elias;
           stabilizationLevel, challengeLevel, autonomyLevel for Kim)
      e. INTERVENTION CONTINUITY BLOCK (Elias only)
         - Active intervention type + therapeutic goal
         - Linked zone + severity
         - Expected shift (from → to)
         - Effectiveness score (/100)
         - Turns active
         - Last user response pattern
         - Zone stability instruction (re-evaluate or continue)
         - Effectiveness-based instruction (working/moderate/low)
         - User response instruction (deflected/escalated/ignored warnings)
         - Zone evolution trail (last 5 entries max)

  11. "Deze gedragsinstructies zijn ABSOLUUT."

  12. HUIDIGE TOESTAND (current state)
      - Mood sliders
      - Urgency level
      - Risk score (/10)
      - Session info (number, duration, emotions, stage)

  13. LIVE SESSION CONTEXT (from bufferSnapshot, if available)
      - Zone, emotional direction, live intent, dominant state

  14. MODULE INSTRUCTIONS (dominant therapeutic module)

  15. CRISIS INSTRUCTIONS (if crisisLevel >= 1)

  16. SESSION END INSTRUCTIONS (if __SESSION_END__ message)

  17. RESPONSREGELS (response rules)
      - Language matching, brevity, no diagnosis, no lists, no emoji excess
      - Character consistency, reflective listening


=== LIVE_MESSAGE (FOLLOW-UP) PROMPT STRUCTURE ===

  1. IDENTITY (same as session start)

  2. ANTI-HALLUCINATION PROTOCOL (same)

  3. CONDITIONAL CONTEXT (selectively injected from cache)
     - resolveConditionalContext() determines which cached fields are relevant for THIS message
     - May include: contextLine, relationshipAnchor, relationalPattern, coreWound, recentDiary, stageOfChange, relationshipMap
     - Only included when message content triggers relevance

  4. LIFE STORY CONTEXT (always, from cache — so GPT knows names/relationships)

  5. USER NAME INSTRUCTION

  6. SELECTIVE RELEVANCE BLOCK
     - Active triggers (always, re-analyzed per message)
     - Conditional fields from step 3

  7. === VERPLICHTE GEDRAGSINSTRUCTIES === (same structure as session start)
     a. Stance
     b. Guidance depth
     c. Regulation instruction
     d. Engine directive
     e. Intervention continuity

  8. "Deze gedragsinstructies zijn ABSOLUUT."

  9. HUIDIGE TOESTAND (same as session start)

  10. LIVE SESSION CONTEXT (bufferSnapshot)

  11. MODULE INSTRUCTIONS

  12. CRISIS INSTRUCTIONS

  13. SESSION END INSTRUCTIONS

  14. RESPONSREGELS (same)

1. Kim Continuity Layer: BLOCKED

2. Cross-Session Learning: NOT IMPLEMENTED
   - getSessionSummary() exists as a pure function (read-only snapshot)
   - NOT connected to any persistence layer
   - Storage contract: "local within-device memory only (AsyncStorage)"
   - No durable learning until database migration is complete
   - No cross-session claims anywhere in the codebase

3. Effectiveness Thresholds (Fix 2 Status):
   - buildInterventionContext() uses hardcoded cutoffs: >= 70 = "working", 40-69 = "moderate", < 40 = "low"
   - These are NOT derived from zone definitions
   - The computeEffectiveness() function itself uses zone-aware scoring:
     * +20 per improved turn (zone severity decreased)
     * +5 per stable turn
     * -15 per worsened turn (zone severity increased)
     * +5 for 'engaged' user response
     * -10 for 'escalated' user response
     * -5 for 'deflected' user response
   - The SCORING is zone-derived (uses severity comparisons)
   - The THRESHOLDS for GPT instruction (70/40) are fixed cutoffs
   - Rationale: these thresholds define GPT behavior categories, not zone-specific values.
     A score of 70+ means "intervention is working" regardless of which zone the user is in.
     The zone influence is already embedded in HOW the score is computed (severity deltas).
   - CONCLUSION: Fix 2 is architecturally complete. The effectiveness COMPUTATION is zone-derived.
     The instruction thresholds (70/40) are intentionally fixed behavioral categories.

4. UserDat Promotion:
   - Promotion only happens at session end (not per-message)
   - Top 5 ranked by score (not FCFS)
   - 24h cooldown per pattern
   - Threshold: repeatCount >= 3

5. Model Routing:
   - Single model per message (never two calls)
   - gpt-4o for high-stakes (crisis, session start, complex modules)
   - gpt-4o-mini for everything else
   - Crisis fallback: if GPT call fails AND crisisLevel >= 1, returns static Dutch response
     with 113 (zelfmoordpreventie) and 112 (nood) numbers. No generic error thrown.
     ← NEW (Round 2 Fix 4, server/ai-chat.ts lines 1237-1263)

6. Buffer vs UserDat:
   - Buffer = live session state (volatile, resets per session)
   - UserDat = persistent state (survives sessions, stored in AsyncStorage)
   - Backpack = stable identity (NEVER modified by pipeline)
   - Full buffer NEVER goes to GPT — only BufferSnapshot (subset)
